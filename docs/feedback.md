# InnoForge 用户反馈记忆 / Feedback Memory

> 记录用户对 AI 的纠正、认可与边界澄清。格式：每条含 规则 / 原因 / 适用场景 / 时间。
> 既记纠正也记认可，避免 agent 越来越保守。命中即记，一次性流水账不沉淀。

## [2026-08-12] 调研外部项目时，用户能打开的链接不代表 AI 索引能查到
- **类型**: 纠正 / 边界
- **规则**: 当用户给出具体的 GitHub/Gitee 仓库 URL，而我的 web_search 搜不到时，不要断定「仓库不存在」或「用户记错了」。我的搜索只走外部索引，对极小或极新的项目经常遗漏。应如实告知用户工具能力边界，并主动改用用户可提供的本地文件（如解压的 ZIP 包）或直抓文件内容来核实，而不是反复用索引搜。
- **原因**: 索引覆盖 ≠ 仓库存在。否定用户「我确认能打开」会显得 AI 不可信；真正的做法是承认限制、换路径取证。
- **适用场景**: 用户给出外部仓库链接、AI 搜索无结果但用户坚持能打开时。
- **时间**: 2026-08-12

## [2026-08-12] 借鉴外部项目要提炼「行为规则」，不要照搬目录结构
- **类型**: 认可 / 边界
- **规则**: 借鉴外部项目时，应优先提炼其行为约束/方法论（检索规则、存储触发器），再决定如何映射到本项目；对目录结构、模板文件、install 脚本这类「外壳」，只对刚初始化的项目有价值，对已运营的成熟项目照搬只会增加空文件和负担。默认先讲清借鉴什么、不借鉴什么，再落地最小改动。
- **原因**: 外壳可复制，方法论才有复用价值；成熟项目最大风险是过度工程化，不是缺少目录。
- **适用场景**: 用户要求「把某个外部项目/技能借鉴进本项目」时。
- **时间**: 2026-08-12

## [2026-08-15] 用户需要把研创台讨论「原样」导出，以便喂给其它 AI 做交叉核对
- **类型**: 认可 / 需求边界
- **规则**: 当用户说「我要把对话导出给其它 AI 验证」时，要导出的是**原始聊天记录**（用户提问与 AI 回复的逐条对话，含时间顺序），而不是整理后的结论摘要。「导出结论」满足的是 AI 归因/归总，「导出对话」满足的是给另一个 AI 复看原始语境做交叉核对——两者并存，不要二选一，也不要默认「整理后再导出」。
- **原因**: 用户明确说「对话里面有很多无效的是放在里面还是要整理呢」——他要的是原始材料的完整语境，让另一个 AI 自行判断哪些有效、哪些无效，而不是由我方预整理。预整理反而可能丢掉那个 AI 需要看到的噪音/推理痕迹。
- **适用场景**: 用户要求把本项目内 AI 对话导出给其它 AI 使用/验证时。默认导出格式为干净 Markdown（不含图片 base64、不含内部推理等噪音），保留逐条角色+内容+时间。
- **时间**: 2026-08-15

## [2026-08-15] 重构的主轴是产品能力，不是代码整洁（方向性纠正）
- **类型**: 纠正 / 方向
- **规则**: 用户说「完整重构」时，动机是**产品功能达不到预期**，不是代码结构不整齐。任何只优化结构、保持行为不变的方案都会被判定为没对齐。规划时必须先问/先验证功能差距，再决定结构工作的取舍。
- **原因**: 用户原话：「我既然想说重构，肯定是里面很多功能达不到预期，要不我为什么不是修修补补就用呢？」结构漂亮的旧产品对他没有价值。
- **适用场景**: 本项目一切后续规划任务。已确认的真实痛点：①检索经常失败、要中文给英文、用自己名下专利测试结果不全、数据不新；②AI 分析不够深不够专、有幻觉、丢上下文；③前端不挑剔（非重点）；④性能尚可（非重点）。目标形态=个人本地利器；检索→创意验证→OA 全流程主线全要。
- **时间**: 2026-08-15

## [2026-09-19] 角色边界：本会话只写方案下发，施工一律交执行 agent
- **类型**: 边界澄清 / 分工
- **规则**: 规划会话（与用户直接对话写方案的会话）只负责：写/改方案文档、以 docs commit 形式下发、里程碑验收审计、方案冲突修订。不亲自执行清场、写产品代码、跑施工类门禁——即使方案里定义了"第 0 段清场"这类前置动作，也交由执行 agent 按 MASTER 下一步清单接手。
- **原因**: 用户明确说「你负责写方案，执行交给其它AI来运行」；且 MASTER 角色分工硬约束早已规定规划会话不写产品代码。规划/执行混岗会让进度记录失真（谁做的、做到哪一步说不清）。
- **适用场景**: 本项目所有规划任务。方案写完后的标准收尾动作是：更新 MASTER 唯一入口 + 下发 docs commit，而非自己动手施工。
- **时间**: 2026-09-19

## [2026-09-19] 执行改动一律走 PR（分支→审阅→合并），不直接提交主干
- **类型**: 边界澄清 / 工作方式
- **规则**: 执行 agent 的交付以 PR 为单位：从 main 开 `exec/*` 分支施工，push 后开 PR，**合并由用户审阅决定，执行 agent 禁止自行合并**；main 在合并前保持不动。规划会话下发的 docs 小提交可直进 main，但涉及 src/templates 的一切变更必须走 PR。
- **原因**: 用户原话「开PR方式来做，这样不会把前面的搞坏了」——交棒期工作区有大量来历不明的未提交改动，直接在 main 上提交/分诊有破坏既有状态的风险；PR 提供审阅关卡和回退参照。
- **适用场景**: 本项目所有执行任务（清场、M-A/M-B/M-C 各任务同样按"一任务一分支一PR"或按里程碑聚合 PR 执行）。
- **时间**: 2026-09-19
