## 1. 产品定位（不变的部分）

面向**发明人/工程师本人**的 AI 专利全流程本地利器：检索现有技术 → 验证创意 → 答复审查意见。
**目标形态：个人本地利器** —— 不做多人/账号/公网部署，安全投入仅保留本地基线。

## 2. 痛点 → 根因诊断 → 需求（P0 主轴）

### 痛点一：「经常搜索失败 / 要中文给我英文 / 自己名下的专利搜不全 / 数据不新」

| 根因（代码证据） | 需求 |
|---|---|
| 在线源只剩 SerpAPI 一条腿（其余全屏蔽），单点失败即全线失败 | **N1 多源冗余检索链**：SerpAPI / EPO OPS / PatentsView / Google Patents 直抓 ≥3 路可用，失败自动降级重试 |
| google_patents 引擎未显式传 country/language，全球库混排 | **N2 中文一等公民**：query 构造带 `country=CN&language=zh` 显式参数；检索页提供「辖区/语言」过滤，默认 CN+zh |
| 申请人匹配无精确增强；FTS5 本地索引靠 save_patent 手动同步，绕过即失联 | **N3 召回保障**：申请人精确匹配模式；检索结果强制入库+自动建索引；本地库作为兜底可搜层 |
| 检索失败黑盒，用户不知道哪个环节挂了 | **N4 检索诊断可见化**：每次检索展示各源成功/失败/耗时/命中数 |

**验收口径**：
- [ ] 用「申请人=本人姓名」中文搜索，首屏出现自己名下专利（用户亲测口径）
- [ ] 默认配置下中文关键词检索，首页中文专利占多数；切换开关可查全球
- [ ] 人为使 SerpAPI 失败（改错 key），系统自动切备用源仍出结果，诊断面板标红失败源
- [ ] 任一次检索的全部结果可在断网后从本地库再次检出

### 痛点二：「AI 分析不够深不够专 / 幻觉 / 丢上下文」

| 根因（代码证据） | 需求 |
|---|---|
| 事实核查引擎写好却未接线（fact_check.rs 零调用） | **N5 幻觉防线激活**：fact_check 接入 OA 与创意分析全流程 |
| 分析上下文是截断文本而非专利全文；RAG 管道是死代码 | **N6 全文喂给 AI**：分析前自动拉取 top-N 专利全文切片进上下文（rag 重写接线） |
| idea 聊天用压缩摘要合并历史（400 行压缩算法），细节必丢；OA 有 60k/40k/15k 静默截断 | **N7 上下文治理**：分级保留策略——关键事实（专利号/日期/claims）结构化传递永不摘要；超限报错不截断 |
| prompt 散落 24+ 处、无领域知识注入、单模型串行 | **N8 专业深度**：领域 prompt 库（IPC 体系/撰写规范/OA 论证结构）+ 专家模型分工（ai_model_expert 已有位子）+ 结论强制带出处 |

**验收口径**：
- [ ] 抽查分析报告 10 条事实性结论，≥9 条带出处（专利号+段/权号）；无源的明确标【推测】
- [ ] 幻觉拦截用例集全过：诱导编造法条页码时，输出被核查标记或拒绝
- [ ] 同主题连续 20 轮对话，首轮关键约束（如"只考虑 CN 专利"）仍生效
- [ ] 深度模式创意报告引用 ≥5 篇专利的全文片段（非摘要）

### 痛点三/四：前端不挑剔、性能尚可 ⇒ **降级处理**

前端只做新功能所必需的 UI 改动 + innerHTML 高危审计（安全底线）；性能只在数据增长后被动优化。**原 v3 方案中 workspace 化、巨型文件全面拆分、前端组件化等任务全部移出主线**，仅在与新功能冲突时局部整理。

## 3. 非目标（本轮明确不做）

- 多人协作/账号体系/公网部署加固
- 前端框架现代化、构建工具引入
- WASM 实验沙箱激活（维持 WIP）
- 真·嵌入模型语义检索（先把 char-TFIDF 修对，做强另立项）

## 4. 里程碑（功能驱动）

```
M-A 可信中文检索   ← 一切的上游，最先做（承载 N1-N4）
M-B 可信深度分析   ← 承载 N5-N8，依赖 M-A 的检索质量与全文获取
M-C 全流程贯通     ← 检索→创意验证→OA 数据打通 + 交付边界最后一公里
```

结构支撑件（从 v3 降级挂载）：T0 地基卫生全套 ✅/进行中、类型与配置地基（T1.1/T1.2 缩水版：只拆新功能要碰的域）、SearchProvider/Embedder 端口（T2.1/T2.2——它们就是 N1/N6 的实现载体）、PDF 提取策略化（T2.5 服务全文获取）。其余结构任务归档备查。
