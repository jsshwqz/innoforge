## 3. 提升路线（四段，按可开工粒度排）

### 第 0 段：清场（任何 M-A 任务的前置，预计半天～1 天）

1. **未提交改动分诊**：逐文件确认 14 处改动的来源（pipeline 四步 + routes 五个 + db 两个 + lib/main）。实质改动→按"一个任务一个 commit"补齐说明后提交；纯 fmt 漂移→单独 chore 提交；判断不了的→ stash 或另建 `wip/` 分支保存，禁止直接丢弃（规约：禁止覆盖用户未提交工作）。
2. **门禁基线回归**：`cargo fmt --check` + `cargo clippy --all-targets -- -D warnings` + `cargo test` + `node check_html_functions.mjs` + `node e2e_test.mjs` 全绿，作为开工基线。
3. **文档基线校准**（docs 提交）：MASTER §5 与 task-breakdown 回写实测——MA3/MB1 标"部分完成+剩余口径"，防重复施工。

### 第 1 段：检索员上岗（M-A，建议 1～2 周）

施工依据不变：`docs/analysis/search-sources-spec.md`。相对 task-breakdown 原序，建议一处顺序调整：

```
MA1 契约+SerpAPI迁入 → MA2 Google Patents XHR直抓（免费无Key，见效最快、可立即验证降级链）
→ MA5 诊断面板（提前到 MA3 前：有了面板，后续每个源的验收都可目测）
→ MA3 中文默认策略（在已有 country 透传基础上补 language/辖区过滤，工作量减半）
→ MA4 召回增强（强制入库+FTS单一写入口） → MA6 SerpAPI稳健化（熔断冷却）
```

**验收加一件**：用用户名下真实专利号建一组固定回归用例（中文关键词 + 申请人精确匹配），每次 M-A 相关改动跑一遍——这是 PRD"用户亲测口径"的自动化形态，也是防回退资产。

### 第 2 段：分析师可信（M-B）

建议顺序（与 task-breakdown 原序的差异及理由）：

```
MB2 全文接线（深度分析的地基，且第1段 MA4 已保证全文可得）
→ MB6 出处标注（先于 MB5/MB3：结构化输出契约一旦定型，OA 线即可同步复用，见第 3 段）
→ MB7 决策段（依赖 MB6 的证据编号体系）
→ MB1 补半程（仅 idea/流水线接线 + 幻觉拦截用例集建库）
→ MB4 上下文治理 → MB3 Embedder 修对 → MB5 prompt 收拢
```

MB5（prompt 库）价值偏工程整洁，在能力跃迁语境下降为段内最后；MB3 中文 panic 修复若期间被检索/切片路径触发，可提级。

### 第 3 段：贯通与北极星实测（M-C）

- MC1/MC2 按原定义执行；**MC2 增加一条**：OA 答复书输出采用 MB6 同一出处契约，全产品线只维护一套"可信报告格式"。
- 收尾验收不看勾选，看北极星三判据的**一次真实全程**：一个真实点子 → 验证报告（每条结论带出处）→ 明确申请/放弃/转向决定 → 一份 OA 意见陈述书 DOCX，全程不开第二个工具核对。实测记录存档 `docs/records/`。

## 4. 机制加固（防再次停摆，均为低成本项）

1. **主控进度按任务粒度回写**：MASTER §3 的 `0/6` 计数每次任务提交时同步；每个执行会话结束前必须有一个（哪怕是 docs 的）提交，"当前状态"节是下一任的唯一入口。
2. **关键路径切成"半天可完成"的开工包**：停摆的直接原因往往是任务入口太重。MA1 的开工包定义即"trait 建模 + SerpAPI 迁出 routes/search.rs，行为不变，门禁全绿"——单会话可完成。
3. **验收以可测口径为准，不以 checkbox 为准**：本次核对发现文档进度落后于代码（MA3/MB1 半程已完成），checkbox 双向失真。规则：勾"完成"必须附验证证据（测试名/命令输出/截图路径），勾"未动"前先 grep。
4. **速查数字以源码为准**（AGENTS.md 第六节已有提醒，执行中强化）：本方案所有差距判定均给出文件行号证据，后续方案同理，禁止引用记忆或旧文档数字下结论。
