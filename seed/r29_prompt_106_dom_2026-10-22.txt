【唯一任务：#106 的真实 DOM 断言 + 顺带修掉 #111 的死代码 guard】
═══════════════════════════════════════════

**背景（已核实的产品缺陷 #111）**：`templates/office_action_response.html` 两处（约 `:1348` 与 `:1586`）都有前置 guard：

```js
if (data.error && data.parsed !== true) { alert(data.error); return; }
```

而后端 `parse_quality_score` 在模型输出解析失败时**必然同时**给出 `parsed:false` **和**非空 `error`（例如 `Failed to parse model output as JSON: …`）。于是这个 guard 恒真，先 `alert(后端英文串)` 后 `return`，导致后面的
`if (data.parsed === false) { … t('oa.quality.parseFailed') … }`
双语失败文案分支**一次都执行不到**。用户看到的是英文后端串直出的 alert + 空白正文，这既违反 #106 的验收（要中英双语文案、不许后端串当 UI），也是 DS 已裁定的 **B 方案里"parsed=false 要显示明确失败文案"** 未真正实现。

**做法（严格按这个顺序，这就是正向与负向证据）**：

1. **先写"红"的测试**：用**真实失败响应**驱动渲染 —— 即 `parsed:false` 且 `error` 非空（就是后端实际返回的样子），断言渲染产物里出现 `oa.quality.parseFailed` 对应的中英双语文案、且**没有** `undefined`/`NaN`/`0/10`、并且**没有**走 `alert`。此时测试必须**红**。**明确禁止**再用 `error:""` 或任何绕过 guard 的输入去"测渲染分支"——那是掩盖，上一轮就是这么做的，本轮视为不合格。
2. **再做最小修正**：把 `parsed` 的判定放到 `error` guard **之前**，**两处同改**，例如先 `if (data.parsed === false) { …渲染失败UI并 return; }`，再 `else if (data.error) { alert(data.error); return; }` 处理传输/后端层失败。不许改响应契约（字段名、类型、`parsed`/`score`/`max`/`dimensions` 的语义都不动），不许顺手做别的功能。
3. **变绿**，并且补一条 `parsed=true` 的 DOM 断言：渲染产物必须出现总分数值与 `/10`、六个维度名、等级；不得出现 `undefined`/`NaN`。
4. 再补一条 guard 顺序的**回归护栏**：把 `parsed:false` + 非空 `error` 喂进去，断言不触发 `alert`（可在测试里桩掉 `window.alert`/或统计调用），证明失败路径不再被 alert 吞掉。

**DOM 断言的实现方式**：优先复用仓库已有的 headless 设施（`e2e_test.mjs`、`check_html_functions.mjs` 这类，或 node 直接抽取模板里的渲染函数执行并检查输出字符串）。要求是**对渲染产出的 HTML/文本做断言**，不是对接口 JSON 做断言；上一条 #106 契约测试已经存在且保留，两者互补，不许把"接口字段断言"再冒充 DOM。若新增辅助脚本，放在 `tests/`（如 `tests/dom_render_106.mjs`）并让它被 Rust 测试调用。

**可证伪要求（写进 commit 正文）**：
- 第 1 步的"红"要在修正前真实复现一次（记录输出）。
- 另外再做一次：把模板 guard 改回旧顺序（或 `git show` 旧版模板），DOM 断言必须**红**；恢复后**绿**。
- 若顺手改了模板里 i18n 键名（例如把 `oa.quality.parseFailed` 改错），也必须能让测试红 —— 用来证明断言真的锚在文案上而不是恒真。
