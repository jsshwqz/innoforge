## 现状（锚点）
`src/error.rs` 的 `enum AppError { NotFound, BadRequest, Internal }`，`IntoResponse` 把 `Internal` 一律映射成 **HTTP 500**，且响应体只有 `{"status":"error","message":...}`，没有机器可读的错误类别。上游 AI/搜索调用返回的 **429/504/422/503**（限流/超时/不可处理/暂不可用，属**可重试**）与真正的服务器内部错误，用户与前端无法区分。

## 要做
1. 给错误响应**增加机器可读 `error_kind`**（保留既有 `status`/`message` 键不变，向后兼容）：
   - 建议取值：`retryable_upstream`（上游 429/504/422/503）、`bad_request`、`not_found`、`server`。
2. `AppError` 增加一个能表达"上游可重试错误"的变体（如 `Upstream { code: u16, message }`），其 `into_response`：
   - 429 → 客户端 HTTP 429；504 → 504；503 → 503；422 → 422（或统一 502/503，但 `error_kind` 必须是 `retryable_upstream`，且**不得**是 500）；
   - 响应体带 `error_kind: "retryable_upstream"` 与原始 `code`。
3. 把 AI/搜索 provider 调用栈里"上游非 2xx / 超时"的失败，落到这个变体（而非 `Internal`）；真正的内部逻辑错误仍是 `Internal`→500/`error_kind:"server"`。审计 `src/routes/search.rs`、`src/ai/*`、`src/search/providers/*` 里把上游失败笼统 `Internal(...)`/500 的位置，统一改到新变体。
4. 不改变任何**成功**响应；不改既有 `status`/`message` 语义（只加 `error_kind` 等新键）。

## 验收（双向负控）
- 正：构造上游返回 429 / 504 / 422 / 503，断言响应 `error_kind == "retryable_upstream"` 且 HTTP 非 500（分别对应 code）；构造 500/一般内部错误，断言 `error_kind == "server"` 且 500。
- 负-底线：把分型退化回"一律 Internal→500" ⇒ 上述 retryable 用例**必红**（证明测试锚在分型上，非恒真）。
- 测试文件：新增 `tests/issue_76_error_taxonomy.rs`，用进程内 stub（`TcpListener::bind("127.0.0.1:0")`）让上游返回各状态码，打真实端点断言。**并用 `--test-threads=1` 稳定复跑**。
