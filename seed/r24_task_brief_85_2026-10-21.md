【要做的事】
1) **排序真按命中 token 数**：`src/db/patent.rs` 的 `search_like` 多 token 分支，`ORDER BY (每个 token 命中计数) DESC, filing_date DESC`。
   - 计数在 SQL 内做：每 token 一个 `CASE WHEN <该 token 的命中表达式> THEN 1 ELSE 0 END` 求和。
   - **硬约束**：排序表达式用的列集合必须与 `WHERE` 里那串 OR LIKE 的列集合**逐字相同**。不许出现"WHERE 查 3 列、ORDER BY 只数 2 列"这种口径分裂——那会产生"结果集里有它但排序数不到它"的新缺陷。建议把列清单提成一个常量/局部变量，WHERE 与 ORDER BY 共用同一份，并在代码注释里写明这是本单的核心不变量。
   - `filing_date DESC` 只作为**同分兜底**，保证测试确定性。
2) **分页语义必须一致**：排序发生在取页之前（SQL 内 ORDER BY + LIMIT/OFFSET），不许"先按日期取一页、再在内存里按相关性重排这一页"——那只会让每页内部看似有序、跨页全乱，是更隐蔽的错。`count_sql` 与 `data_sql` 的 WHERE 保持同源。
3) **`relevance_score` 与排序口径对齐**：现在 `calculate_mixed_relevance` 算了分却不参与排序。要么让展示分与实际排序同源（推荐：排序就用命中计数，展示分继续由 `calculate_mixed_relevance` 出，但要在 `docs/API.md` 写清两者的关系），不许留"分高却排在后面"的第三种状态。
4) **文档同步**：`docs/API.md` 该段落要把排序规则写成可验证的表述（命中 token 数优先、同分按申请日倒序、排序与过滤同列集）。**不要动 `docs/errors.md` 与 `docs/plans/STATUS.md`**（Doc Staleness 门禁由指挥方在同一 PR 补，避免追加冲突）。
